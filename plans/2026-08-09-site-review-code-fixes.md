## Phase 2 — SEO structure

### 2.1 Sitemap lists only `/`
`app/routes.py:34`. `/dog` and `/dog/about-crawler` are both prerendered (`nuxt.config.ts:21`) and linked from the footer, and `about-crawler` exists specifically so crawler operators can find it — it should not depend on them guessing the URL. ### 2.2 Soft 404s — every unknown URL returns HTTP 200

`app/routes.py:79` serves `200.html` with a 200 status for anything that isn't a real file, and `frontend/pages/[...slug].vue` sets no robots directive. Search engines index junk URLs as real pages.

Two independent parts; ship both.

**(a) `noindex` on the 404 page.** Add a `useHead` with `{ name: 'robots', content: 'noindex' }` to `frontend/pages/[...slug].vue`. Zero risk, works immediately.

**(b) Correct status code from Flask.** Return **404 with the same `200.html` body** for paths outside a known-route allow-list, so the client-side router still renders the styled 404 page while crawlers see the right status.

Implement a shared helper — call it `is_known_route(path)` — listing the SPA route prefixes: `/login`, `/admin`, `/recipes`, `/dog`. Anything matching a prefix keeps its 200 (this is what makes non-prerendered routes like `/recipes/<slug>` work); anything else gets the 404 status with the identical body.

Be careful with the ordering: the existing `os.path.isfile` / directory-`index.html` branches above must be left untouched, so real static assets are unaffected. Only the final fallback line changes. `/api/*` never reaches `catch_all` — the blueprints match first — so it is out of scope here.

This helper is reused by 4.3, so put it somewhere both modules can import.

**Tests:** no test file currently covers `sitemap.xml` or `catch_all` — add `tests/test_core_routes.py`. Cover: sitemap contains all three URLs and is well-formed XML; a known SPA route returns 200; an unknown path returns 404 *with the SPA shell body*; a real static asset still returns 200. `frontend/e2e/not-found.spec.js` already exists — extend it to assert the response status rather than only the rendered heading.

## Phase 3 — Frontend bugs

### 3.1 `loadHomeContent` replaces the locale map instead of merging it — latent live breakage
`frontend/stores/i18n.js:57`:
```js
homeContent.value = { ...homeContent.value, [loc]: data }
```
`home.*` **content** keys have no fallback in `locales/{en,fi}.json` — the build snapshot is the only backstop, and this line discards it wholesale. Any key present in the snapshot but not yet seeded in the production DB is therefore *deleted* by the runtime fetch, and `resolveRaw` falls through to returning the raw key, so the page paints a literal `home.hero.eyebrow`. That makes "add a new home content key" a two-step deploy where step one visibly breaks the live site.

Merge instead:
```js
homeContent.value = {
  ...homeContent.value,
  [loc]: { ...homeContent.value[loc], ...data },
}
```
Merging is safe here because `HOME_CONTENT_FIELDS` keys can only be upserted through the API, never deleted (`app/home_content.py:207-234`), so a stale snapshot value can never mask an intentional deletion. `home.projects` is an array and is still replaced wholesale, which is the desired behaviour for the collection.

**Test:** `frontend/tests/unit/stores/i18n.test.js` — assert a snapshot key absent from the fetch response survives `loadHomeContent()`.

### 3.2 `t()` interpolates only the first occurrence of a placeholder
`frontend/stores/i18n.js:38` uses `String.replace` with a string needle, which replaces one occurrence. Switch to a global regex. Keys are simple identifiers, but escape the key anyway rather than interpolating it raw into a `RegExp`.

**Test:** same file — a message repeating `{count}` twice.

### 3.3 Mobile nav drawer keeps focusable links inside `aria-hidden="true"`
`frontend/components/home/HomeHeader.vue:67`. The drawer collapses with `max-height: 0; overflow: hidden`, so its links stay in the tab order while `aria-hidden` removes them from the accessibility tree — the canonical axe violation ("focusable element inside `aria-hidden`"), on a site that advertises accessibility in its own stack table.

Add `:inert="!menuOpen"`. That removes the links from both the tab order and the a11y tree, and lets `aria-hidden` go entirely.

**Test:** extend `frontend/e2e/homepage.spec.js` — at mobile viewport with the drawer closed, tabbing from the hamburger must not land inside the drawer.

### 3.4 Project links get no `target` / `rel`; footer links do
`frontend/components/home/HomeWork.vue:55` renders admin-authored links bare, while `HomeFooter.vue:30-31` does the `isExternal` → `target="_blank"` + `rel="noopener noreferrer"` treatment. Same data shape, two behaviours.

Lift `isExternal` out of `HomeFooter.vue:10-12` into a shared composable and use it in both. `composables/useLinkIcon.js` is the natural home — it already exists to answer "what kind of link is this?" — so extend it to return both `linkIcon` and `isExternal` rather than adding a second one-function composable.

### 3.5 `useLinkIcon` gives internal links the outbound arrow
`frontend/composables/useLinkIcon.js:11` — the fallback is `solar:arrow-right-up-bold`, which conventionally means "leaves this site". `#stack` and `/dog` both get it today. Return a neutral glyph for relative/anchor hrefs and keep the diagonal arrow for genuinely external ones — the `isExternal` predicate from 3.4 is exactly the test needed.

Any new icon name must be added to the `icon.clientBundle.icons` array in `nuxt.config.ts:46-75` — these names are resolved dynamically and `scan` cannot see them, and `fallbackToApi` is `false`, so an unlisted icon silently renders nothing.

**Test:** `frontend/tests/unit/` — add a `useLinkIcon` spec covering mailto / github / linkedin / anchor / relative / external.

### 3.6 Footer copyright year (code half — read "Cross-plan sequencing" first)
`frontend/components/home/HomeFooter.vue:48` calls `t('home.footer.copyright')` with no params, and the DB value hardcodes `© 2026`, so the footer needs a manual admin edit every January.

## Phase 4 — Backend bugs

### 4.1 GitHub commit-date cache never negative-caches failures
`app/utils.py:29-31`. On exception, `_cached_commit_timestamp` is left untouched, so **every** subsequent `/api/meta` and `/sitemap.xml` request retries a blocking 5-second outbound call. Unauthenticated GitHub API is 60 req/h per IP — once rate-limited or during a GitHub outage, a crawler walking `/sitemap.xml` stalls a Gunicorn worker for 5s per hit. On a Celeron N4505 with a small worker pool that is a real availability dent, and 2.1 is about to make `/sitemap.xml` more attractive to crawlers.

Add a separate `_last_attempt_timestamp` guard with a short negative TTL (~5 min): if the last attempt failed and the TTL has not elapsed, return the stale cache (possibly `None`) without touching the network. Keep the existing 6-hour success TTL as is.

**Test:** `tests/test_utils.py` already covers this function — add a case asserting that two calls following a failure produce exactly one outbound request.

### 4.2 Login is email-case-sensitive
`app/auth.py:34` — `.strip()` but no case handling, while `_email_log_hash` two lines up *does* lowercase. `Konsta@erez.ac` fails where `konsta@erez.ac` works.

Do **not** just lowercase the input: existing rows may store mixed case, and that would lock those accounts out. Compare case-insensitively instead — `User.query.filter(func.lower(User.email) == email.lower())` — which handles both directions without a data migration.

Check `scripts/seed_e2e.py` and `scripts/local-user.sh` for assumptions about email casing while here.

### 4.3 `/api/pageview` allows unbounded growth of a replicated database
`app/api/pageviews.py:12-38`. The endpoint is public, rate-limited to 60/min, and validates only that `path` starts with `/` and is ≤200 bytes — nothing ties it to a real route. Three compounding problems:

- Each distinct path inserts a `PageView` row **and** a `PageViewEvent` row. At the limit that is ~86k junk rows/day into `site.db`, which Litestream then replicates to Backblaze.
- `session["viewed_pages"]` (line 24, appended at line 37) has no cap. It lives in the **signed client-side cookie**, so it is re-sent on every request and eventually trips Werkzeug's 4 KB warning.
- `PageViewEvent` is never pruned anywhere in the repo, even though `/api/pageviews/events` caps its window at 90 days. Rows accumulate forever with nothing reading them.

Fixes, all three:
1. Reject paths that fail `is_known_route(path)` from 2.2(b) — return 400 rather than silently dropping, so a genuine bug in `usePageView` is visible. Confirm `frontend/composables/usePageView.js` only ever sends real route paths before enabling this.
2. Cap `viewed_pages` at a fixed length (50 is plenty given the route count) with FIFO eviction.
3. Add a retention prune for `PageViewEvent` older than 90 days. Put it in `scripts/` as a standalone script rather than in a request path or app startup, consistent with how `dog_crawl.py` is kept out of the web tier.

**Tests:** `tests/test_pageviews.py` — unknown path rejected, known path still counted, `viewed_pages` stops growing past the cap, prune script deletes only rows outside the window.

### 4.4 Login has a user-enumeration timing oracle
`app/auth.py:35` — `check_password` (scrypt, deliberately expensive) runs only when the email exists, so response latency cleanly separates valid from invalid emails. The 3/min limiter blunts this but does not close it.

Compute a module-level dummy scrypt hash at import and verify the supplied password against it on the miss path, so both branches pay the same cost. Low severity; two lines.

### 4.5 `_is_safe_href` accepts protocol-relative URLs
`app/home_content.py:104-111` — `stripped.startswith("/")` matches `//evil.com`, which browsers resolve as an external host, so a stored link can point off-site while reading as internal in the admin. Admin-only, so low severity, but reject a second leading `/` and send it down the scheme check instead.

**Test:** `tests/test_home_content.py` already covers href validation — add `//evil.com`.

Separate repo, separate commits. Its `CLAUDE.md` is **BDD-first**: update or add the matching `features/*.feature` file in the same commit as the code, and run the checks in CI order (typecheck, lint, unit, BDD, E2E, build). Versioning is changesets-based per `CLAUDE.md` — these are `fix:` commits against the server target.

### 5.1 Session expiry is off by up to a full day

Both session stores write `expires_at` with `toISOString()` (`2026-08-09T07:58:26.212Z`) and compare it against `datetime('now')` (`2026-08-09 10:58:26`). SQLite compares those as text, hitting `T` (0x54) vs space (0x20) at index 10 — so **any session whose expiry falls on the current UTC date compares as still valid.** Verified against `better-sqlite3`:

```
expires_at  = 2026-08-09T07:58:26.212Z   (expired 3 hours ago)
now         = 2026-08-09 10:58:26
still valid? 1
```

Affected, same bug in both:
- `server/auth/session.ts:62` — admin sessions, 7-day TTL
- `server/player-auth/session.ts:53` — player sessions, 90-day TTL

The matching `cleanupExpiredSessions` / `cleanupExpiredPlayerSessions` DELETEs use the same predicate, so they silently skip those rows too and the tables retain expired sessions.

Fix by making the comparison date-aware rather than lexical — `datetime(expires_at) > datetime('now')` — in all four queries. Storing the timestamp in SQLite's own text format instead would also work and is marginally faster, but it needs a data migration for existing rows, so prefer the query-side fix unless there is a reason to normalise the column.

**Test:** unit coverage for a session expiring earlier the same UTC day, which is the case that currently passes and must fail. This is the whole bug — a test that only checks "expired yesterday" stays green against the broken code.

### 5.2 Session tokens are stored in plaintext

`sessions.id` and `player_sessions.id` **are** the raw bearer tokens (`auth/session.ts:44`, `player-auth/session.ts:38`). Per this repo's `CLAUDE.md`, `sanakenno.db` is Litestream-replicated to Backblaze B2 — so the complete set of live admin and player tokens sits in off-site backups in directly usable form. Anyone holding a copy of the database or a backup can mint a valid `Authorization: Bearer` for any player or admin without touching a password.

Store `sha256(token)` as the row key and look up by hash; return the raw token only from `createSession` / `createPlayerSession`, which is the only place it should ever exist in cleartext. This is the same reasoning already applied to passwords, and unlike passwords a plain SHA-256 is appropriate — the tokens are 32 random bytes, so there is nothing to brute-force and no need for a slow KDF.

Touches `createSession`, `validateSession`, `deleteSession`, `deleteSessionsForAdmin` and the three player-side equivalents, plus `auth/middleware.ts` and `player-auth/middleware.ts` if they query directly.

**Migration:** existing rows hold plaintext ids that will no longer match. Deleting all rows on deploy logs every admin and player out — acceptable for admins (7-day TTL, one user), **not** for players (90-day TTL, thousands of installs). Decide the strategy before implementing and write it into the plan file: either a one-off migration that hashes existing ids in place (preserves sessions, simplest), or dual-read for a transition window. Recommend the in-place hash migration.

## Deliberately out of scope

Each of these needs its own plan; do not fold them into this work.

- **Index on `PageViewEvent.timestamp`** (`app/models.py:209`) — it is the filter column in the events query (`app/api/pageviews.py:72`) with no index, so every admin analytics load is a full scan over a table that 4.3 shows grows without bound. This is a **schema change**, and `CLAUDE.md` forbids migrations from startup, imports, or request handlers: it needs an explicit plan, test and seed updates, and a reviewed one-off production SQLite migration.
- **`useTerminal.js` module-scope mutable state** (`outputLines`, `hasBooted`, `choreographyController`, and `prefersReducedMotion` captured once at import). Harmless under SSG, but `playwright.config.js` runs `nuxt build` (node-server preset), where module scope is shared across requests and terminal output can bleed between concurrent SSR renders. Refactoring 507 lines of terminal state into a proper store is its own change.
- **Finnish content never reaching search engines or social scrapers** — SSG prerenders English only and the locale flips after hydration, so no Finnish copy is in the static HTML. Fixing it properly means a prerendered `/fi` route tree and is an architecture decision, not a bug fix.
- **All database-owned content** — see the companion plan.

## Security considerations

- **New input vectors?** No new endpoints. 4.3 *narrows* an existing vector by allow-listing `/api/pageview` paths; 4.5 narrows href validation. 2.2(b) changes a status code, not what is served.
- **Exposes internal state?** No. 2.1 adds two already-public URLs to the sitemap. 1.5 adds already-public profile links to JSON-LD. The 404 body is unchanged — only its status code.
- **Weakens the network boundary?** No new ports, origins, or CSP relaxations. No new outbound calls; 4.1 strictly *reduces* outbound traffic.
- **Improves posture:** 4.4 closes a login enumeration oracle, 4.3 closes an unauthenticated DB-growth vector against a replicated database, 5.2 removes plaintext bearer tokens from off-site backups.
